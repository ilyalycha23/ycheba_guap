4. Теоретическая часть 
4.1 App Router как файловый маршрутизатор 
Официальная документация Next.js определяет App Router как файловый маршрутизатор. 
Каталоги задают сегменты URL, а специальные файлы задают поведение и содержимое 
маршрута. Страница создаётся файлом page.tsx, а общая разметка — файлом layout.tsx. 
(Next.js: App Router; Next.js: Layouts and Pages) 
Пример соответствия файлов и адресов: 
app/page.tsx                  → / 
app/start/page.tsx            → /start 
app/catalog/page.tsx          → /catalog 
app/auth/login/page.tsx       → /auth/login 
app/cabinet/page.tsx          → /cabinet 
Каждый page.tsx должен экспортировать React-компонент по умолчанию: 
export default function CatalogPage() { 
  return <h1>Каталог</h1>; 
} 
Корневой layout обязателен. Он принимает children и оборачивает содержимое всех 
страниц. Общая навигация, провайдер состояния и повторяющиеся элементы оболочки 
приложения размещаются в layout или в компонентах, которые он подключает. 
export default function RootLayout({ 
  children, 
}: Readonly<{ children: React.ReactNode }>) { 
  return ( 
    <html lang="ru"> 
      <body>{children}</body> 
    </html> 
  ); 
} 
Согласно официальной документации Layouts and Pages, layout сохраняет состояние, 
остаётся интерактивным и не перерисовывается полностью при переходах между 
вложенными страницами. Это делает корневой layout подходящим местом для общей 
оболочки приложения. 
4.2 Навигация между страницами 
Компонент Link из next/link является основным средством перехода между маршрутами 
Next.js. Официальное руководство Linking and Navigating указывает, что Link 
поддерживает клиентские переходы и предварительную загрузку маршрутов. При 
переходе общая разметка сохраняется, а содержимое текущей страницы заменяется без 
полной перезагрузки документа. 
import Link from "next/link"; 
 
<Link href="/catalog">Открыть каталог</Link> \n3 
 
Обычный элемент a нужен для внешних ресурсов. Для внутренних страниц приложения в 
этой работе применяется Link. 
Текущий путь в Client Component можно получить с помощью usePathname из 
next/navigation. В официальной справке Next.js usePathname описан как клиентский хук, 
возвращающий pathname текущего URL. 
"use client"; 
 
import { usePathname } from "next/navigation"; 
 
export default function CurrentSection() { 
  const pathname = usePathname(); 
  return <p>Текущий путь: {pathname}</p>; 
} 
В учебном приложении usePathname используется для aria-current и визуального 
выделения активного пункта навигации. Он не используется как средство защиты 
страницы. 
4.3 Динамические сегменты 
Если заранее неизвестны все адреса страниц предметных сущностей, Next.js позволяет 
создать динамический сегмент. Согласно официальной документации Dynamic Route 
Segments, имя каталога заключается в квадратные скобки. 
app/catalog/[id]/page.tsx 
Такой файл может обслуживать адреса /catalog/library, /catalog/coworking и другие 
значения id. 
В актуальном App Router значение params является Promise. Его необходимо получить с 
помощью await в асинхронном компоненте страницы. 
export default async function ItemPage({ 
  params, 
}: { 
  params: Promise<{ id: string }>; 
}) { 
  const { id } = await params; 
  return <h1>Объект: {id}</h1>; 
} 
Значение динамического параметра приходит из URL и должно рассматриваться как 
внешнее значение. Если объект не найден, страница может вызвать notFound из 
next/navigation. 
4.4 Server Components и Client Components 
Официальная документация Next.js Server and Client Components указывает, что страницы 
и layouts в App Router по умолчанию являются Server Components. Они подходят для 
статической разметки, получения данных на сервере и сохранения секретов вне 
клиентского JavaScript. \n4 
 
Client Components применяются, когда необходимы состояние, обработчики событий, 
эффекты, пользовательские хуки или браузерные API. Граница клиентской части 
объявляется директивой "use client" перед импортами. 
"use client"; 
 
import { useState } from "react"; 
 
export default function Counter() { 
  const [count, setCount] = useState(0); 
  return <button onClick={() => setCount(count + 1)}>{count}</button>; 
} 
Директива не должна автоматически добавляться во все файлы. Официальная 
документация рекомендует оставлять статические части серверными и выделять 
интерактивность в небольшие Client Components. В этой работе страницы каталога 
остаются серверными, а навигация, провайдер пользователя и формы становятся 
клиентскими. 
4.5 Аутентификация, сессия и авторизация 
Официальное руководство Next.js Authentication разделяет защиту приложения на три 
понятия. 
 Аутентификация подтверждает, что пользователь является тем, за кого себя выдаёт. 
Обычно пользователь предъявляет учётные данные, например email и пароль. 
 Управление сессией сохраняет состояние входа между запросами. 
 Авторизация определяет, к каким маршрутам, данным и действиям имеет доступ 
аутентифицированный пользователь. 
Эти понятия связаны, но не взаимозаменяемы. Отображение формы входа ещё не 
выполняет аутентификацию. Запись имени в React state ещё не создаёт серверную сессию. 
Скрытие кнопки на клиенте ещё не запрещает обращение к защищённым данным. 
В официальном руководстве Next.js показано, что обработка реальных учётных данных и 
серверная проверка выполняются в серверном окружении. Для сессионной cookie 
рекомендуются параметры HttpOnly, Secure, SameSite, Max-Age или Expires и Path. 
Защищённые операции должны повторно проверять права как можно ближе к источнику 
данных. 
В лабораторной работе № 2 эти механизмы только изучаются. Реализуемый 
DemoAuthProvider хранит объект пользователя в памяти вкладки браузера, чтобы 
отработать условный интерфейс и передачу состояния. Он не принимает решение о 
реальном доступе к данным. 
4.6 Контекст и состояние React 
Официальная справка React определяет useState как хук, добавляющий переменную 
состояния в компонент. Вызов функции обновления изменяет состояние и запускает 
повторный рендер. 
const [user, setUser] = useState<User | null>(null); \n5 
 
Контекст позволяет передавать значение глубоко по дереву компонентов без 
последовательной передачи props через каждый промежуточный компонент. Согласно 
официальной справке useContext, компонент получает значение ближайшего 
соответствующего провайдера выше по дереву и подписывается на его изменения. 
const AuthContext = createContext<AuthContextValue | null>(null); 
В корневом layout провайдер оборачивает страницы. Навигация, форма входа и личный 
кабинет получают один и тот же объект пользователя через useContext. 
Контекст не является хранилищем базы данных и не является механизмом безопасности. 
После обновления страницы обычное состояние React создаётся заново. В этой работе 
такое поведение является намеренным признаком учебного прототипа. 
4.7 Формы и проверка данных 
Официальное руководство Next.js Forms указывает, что базовую клиентскую проверку 
можно выполнять HTML-атрибутами required и type="email". Серверная проверка нужна 
независимо от клиентской и будет добавлена позже. 
<input name="email" type="email" required /> 
<input name="password" type="password" minLength={8} required /> 
Элемент label должен быть связан с полем. Ошибка должна выводиться текстом, а не 
только цветом. Для отправки используется обработчик onSubmit, который вызывает 
preventDefault в учебном клиентском прототипе. 
function handleSubmit(event: React.FormEvent<HTMLFormElement>) { 
  event.preventDefault(); 
  // Учебное обновление состояния. 
} 
Наличие minLength или собственной проверки на клиенте улучшает обратную связь, но не 
защищает сервер: HTTP-запрос можно сформировать без интерфейса. Поэтому в отчёте 
студент обязан явно отделить проверку удобства интерфейса от серверной проверки 
безопасности. 
4.8 Связь с архитектурой TheraCity 
В TheraCity корневой app/layout.tsx подключает AuthProvider и общий компонент 
BurgerMenu. Страницы app/auth/login/page.tsx и app/auth/register/page.tsx являются Client 
Components, используют состояние формы и получают функции из контекста. Реальный 
AuthProvider вызывает серверные маршруты /api/auth/login, /api/auth/me и /api/auth/logout. 
В лабораторной работе № 2 используется только архитектурная аналогия: общий 
провайдер, формы и условный интерфейс. Вызовы API, cookie, Prisma и таблица 
пользователей не копируются, потому что соответствующая серверная инфраструктура 
ещё не создана.

Этап 6. DemoAuthProvider 
Создайте app/providers/DemoAuthProvider.tsx. Провайдер должен хранить User | null и 
предоставлять функции login, register и logout. 
Требования к прототипу: 
 объект пользователя содержит name и email; 
 login создаёт учебного пользователя из email; 
 register создаёт пользователя из имени и email; 
 logout устанавливает user в null; 
 хук useDemoAuth сообщает об ошибке, если используется вне провайдера; 
 пароль не сохраняется ни в state провайдера, ни в localStorage, ни в файле. 
Оберните содержимое body провайдером в корневом layout.

// Хранит учебное состояние пользователя и предоставляет вход и выход через React 
Context. 
 
"use client"; 
 
import { 
  createContext, 
  useContext, 
  useMemo, 
  useState, 
  type ReactNode, 
} from "react"; 
 
// Описываем данные учебного пользователя. 
export type DemoUser = { 
  name: string; 
  email: string; 
}; 
 
// Задаём контракт данных и функций контекста. 
type DemoAuthContextValue = { 
  user: DemoUser | null; 
  login: (email: string) => void; 
  register: (name: string, email: string) => void; 
  logout: () => void; 
}; 
 
const DemoAuthContext = createContext<DemoAuthContextValue | null>(null); 
 
// Объявляем основной компонент этого файла. 
export default function DemoAuthProvider({ 
  children, 
}: Readonly<{ children: ReactNode }>) { 
  // Создаём локальное состояние компонента. 
  const [user, setUser] = useState<DemoUser | null>(null); 
 
  // Мемоизируем объект контекста до изменения его зависимостей. 
  const value = useMemo<DemoAuthContextValue>( 
    () => ({ 
      user, 
      login(email) { 
        const name = email.split("@")[0]?.trim() || "Студент"; 
        setUser({ name, email }); 
      }, 
      register(name, email) { 
        setUser({ name: name.trim(), email }); 
      }, 
      logout() { 
        setUser(null); 
      }, 
    }), 
    [user], 
  ); 
 
  // Возвращаем JSX-разметку, которую React выведет на странице. 
  return ( 
    <DemoAuthContext.Provider value={value}> 
      {children} \n15 
 
    </DemoAuthContext.Provider> 
  ); 
} 
 
// Возвращаем контекст и защищаем хук от вызова вне провайдера. 
export function useDemoAuth(): DemoAuthContextValue { 
  const context = useContext(DemoAuthContext); 
 
  if (!context) { 
    throw new Error("useDemoAuth должен использоваться внутри DemoAuthProvider"); 
  } 
 
  return context; 
}
