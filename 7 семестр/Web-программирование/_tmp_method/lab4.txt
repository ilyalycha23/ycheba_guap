. Теоретическая часть 
4.1 Адаптивный веб-дизайн 
MDN определяет responsive web design как подход, при котором страницы хорошо 
отображаются на экранах разных размеров и разрешений и сохраняют удобство 
использования. Это не отдельная технология, а набор практик: гибкая сетка, гибкие 
изображения, современные способы раскладки и media queries. (MDN: Responsive web 
design) 
Фиксированная ширина всей страницы создаёт горизонтальную прокрутку на узком 
экране и лишнее пустое пространство на широком. Адаптивный интерфейс изменяет 
расположение и размеры элементов в зависимости от доступного пространства, а не 
поддерживает отдельную копию страницы для каждого устройства. 
Для StudySpace это означает: 
 карточки перестраиваются из нескольких колонок в одну; 
 текст и отступы плавно уменьшаются; 
 модальное окно не выходит за viewport; 
 панель меню занимает допустимую ширину; 
 карта изменяет высоту и пересчитывает размер контейнера; 
 изображения загружаются в размере, соответствующем их фактическому 
отображению. 
4.2 Viewport в Next.js App Router 
Без корректного viewport мобильный браузер может использовать виртуальную ширину, 
рассчитанную для старых desktop-страниц. MDN показывает базовую настройку 
width=device-width и initial-scale=1. Она связывает CSS-ширину страницы с шириной 
устройства и позволяет media queries работать ожидаемо. (MDN: Responsive web design) 
В App Router Next.js автоматически добавляет два базовых meta-тега: charset и viewport. 
Документация Next.js приводит результат по умолчанию: 
<meta name="viewport" content="width=device-width, initial-scale=1" /> 
Поэтому вручную дублировать этот тег в layout.tsx не требуется. Если нужно настроить, 
например, themeColor или colorScheme, App Router поддерживает статический экспорт 
viewport и функцию generateViewport только в Server Components. (Next.js: Metadata and 
OG images; Next.js: generateViewport) 
import type { Viewport } from "next"; 
 
export const viewport: Viewport = { \n3 
  themeColor: "#f6f3ec", 
  colorScheme: "light", 
}; 
Отключать масштабирование пользователя параметрами maximumScale или userScalable в 
этой работе нельзя: возможность увеличения страницы необходима для ручной проверки 
доступности. 
4.3 Mobile-first и контрольные точки 
MDN описывает mobile-first как подход, при котором сначала создаётся простой 
одноколоночный макет для узкого экрана, а затем media queries добавляют более сложную 
раскладку при появлении достаточного пространства. Контрольная точка, или breakpoint, 
— условие, при котором меняется макет. (MDN: Responsive web design; MDN: Media query 
fundamentals) 
.page { 
  padding-inline: 16px; 
} 
 
@media (min-width: 48rem) { 
  .page { 
    padding-inline: 32px; 
  } 
} 
Контрольные точки выбирают по содержимому: новая точка нужна там, где текущий 
макет становится тесным или неоправданно растянутым. MDN рекомендует не 
привязывать breakpoint к конкретной модели устройства и использовать относительные 
единицы. Набор ширин для отчёта является методикой курса, а не перечнем всех 
существующих устройств. 
4.4 CSS Grid, Flexbox и гибкая сетка 
Flexbox является одномерным способом раскладки по строке или колонке, а CSS Grid — 
двумерной системой строк и колонок. Оба механизма позволяют элементам растягиваться 
и сжиматься без ручного вычисления координат. (MDN: CSS layout) 
Для галереи удобно использовать Grid с minmax(). Функция minmax() задаёт 
минимальную и максимальную границы размера колонки, а auto-fit создаёт столько 
колонок, сколько помещается в контейнере. 
.grid { 
  display: grid; 
  grid-template-columns: repeat(auto-fit, minmax(min(100%, 15rem), 1fr)); 
  gap: 1rem; 
} 
Вложенная функция min(100%, 15rem) не позволяет минимальной ширине колонки 
оказаться шире самого контейнера. Flexbox подходит для строки действий, заголовка 
меню и группы фильтров: 
.actions { 
  display: flex; 
  flex-wrap: wrap; \n4 
  gap: 0.75rem; 
} 
4.5 Относительные размеры, min(), max() и clamp() 
Относительные единицы rem, em, %, vw и vh позволяют связывать размер с шрифтом, 
контейнером или viewport. CSS-функция clamp(MIN, VAL, MAX) ограничивает 
предпочтительное значение нижней и верхней границами. (MDN: clamp())) 
.pageTitle { 
  font-size: clamp(1.75rem, 4vw, 3rem); 
} 
 
.page { 
  width: min(72rem, 100%); 
  margin-inline: auto; 
} 
clamp() полезна для плавной типографики и отступов, но не заменяет media queries, когда 
необходимо структурное изменение: например, перенос панели действий или смена 
направления колонок. 
Для модальных окон используется единица dvh — динамическая высота viewport. Она 
учитывает изменение видимой области на мобильных устройствах, когда панели браузера 
появляются или скрываются. Ограничение max-height и внутренний overflow-y позволяют 
прокручивать содержимое окна, не теряя кнопку закрытия. 
4.6 Media queries по возможностям устройства и 
предпочтениям пользователя 
Media queries могут проверять не только ширину. MDN описывает media features hover и 
pointer для определения наличия удобного наведения и точности основного указателя. 
Эффект, доступный только при наведении, следует включать там, где hover действительно 
поддерживается. 
@media (hover: hover) and (pointer: fine) { 
  .card:hover { 
    transform: translateY(-2px); 
  } 
} 
Media feature prefers-reduced-motion сообщает, что пользователь включил системную 
настройку уменьшения необязательного движения. В этом режиме длительные переходы 
и анимации следует убрать или существенно сократить. (MDN: prefers-reduced-motion) 
@media (prefers-reduced-motion: reduce) { 
  *, 
  *::before, 
  *::after { 
    scroll-behavior: auto !important; 
    animation-duration: 0.01ms !important; 
    animation-iteration-count: 1 !important; 
    transition-duration: 0.01ms !important; 
  } 
} \n5 
4.7 Адаптивные изображения и next/image 
Компонент Image выполняет оптимизацию изображений, поддерживает отложенную 
загрузку и создаёт варианты srcset. Для изображения с fill или изображения, размер 
которого меняется в CSS, документация Next.js требует осмысленное свойство sizes. 
Браузер использует sizes, чтобы выбрать подходящий ресурс из srcset. Если sizes 
отсутствует, браузер предполагает ширину 100vw, что может привести к загрузке 
слишком большого файла. (Next.js: Image Component) 
<Image 
  src={place.image} 
  alt={place.imageAlt} 
  fill 
  sizes="(max-width: 47.99rem) 100vw, (max-width: 74.99rem) 50vw, 33vw" 
  className={styles.image} 
/> 
Контейнер с fill должен иметь позиционирование, а aspect-ratio резервирует устойчивую 
область до загрузки изображения: 
.imageWrap { 
  position: relative; 
  aspect-ratio: 3 / 2; 
  overflow: hidden; 
} 
 
.image { 
  object-fit: cover; 
} 
Свойство preload или высокий fetchPriority применяют только к обоснованному LCP-
изображению над первым экраном. Предзагрузка всех карточек конкурирует за сеть и не 
является оптимизацией. 
4.8 Адаптивность модального окна, меню и карты 
Адаптивное модальное окно должно сохранять требования лабораторной работы № 3: 
доступное имя, роль dialog, aria-modal, закрытие Escape, цикл Tab и возврат фокуса. 
Изменение визуального размера не должно ломать клавиатурную модель. 
На узком экране overlay получает меньшие отступы, dialog ограничивается шириной и 
динамической высотой, а его содержимое прокручивается. Кнопки не должны выходить 
за область окна. 
Панель бургер-меню может занимать всю ширину телефона и ограниченную ширину на 
desktop. Состояния :focus-visible сохраняются на всех контрольных точках. Закрытая 
панель не должна оставаться поверх страницы или перехватывать указатель. 
Контейнер карты изменяет размер вместе с макетом. ResizeObserver по документации 
MDN сообщает об изменении размеров элемента. После изменения контейнера API карты 
необходимо уведомить вызовом map.container.fitToViewport(), предусмотренным API 
Яндекс Карт. Наблюдатель отключается в cleanup, а карта уничтожается. \n6 
4.9 Что проверяет Lighthouse 
Lighthouse — открытый автоматизированный инструмент для улучшения качества веб-
страниц. Его можно запускать в Chrome DevTools, из командной строки или как Node-
модуль. Инструмент получает URL, выполняет набор аудитов и формирует отчёт с 
объяснениями проблем и ссылками на способы исправления. (Chrome for Developers: 
Introduction to Lighthouse) 
Панель Lighthouse в Chrome DevTools формирует отчёты по категориям: 
 Performance — показатели загрузки и выполнения страницы; 
 Accessibility — автоматически обнаруживаемые проблемы доступности; 
 Best Practices — состояние и общие практики клиентского кода; 
 SEO — базовые возможности индексации и поискового представления. 
Число категории — агрегированная оценка, а не перечень всех ошибок. В Performance 
непосредственно в оценку входят метрики; разделы Opportunities и Diagnostics помогают 
искать причины и влияют на оценку косвенно через изменение метрик. (Chrome for 
Developers: Lighthouse performance scoring) 
4.10 Режимы и воспроизводимость запуска 
Официальное руководство Chrome DevTools предлагает сначала сохранить baseline — 
результат до улучшений. Для проверки загрузки страницы в этой работе используется 
Mode: Navigation. Device: Mobile изменяет user agent и моделирует мобильный viewport. 
По умолчанию применяется simulated throttling, которое оценивает поведение при 
ограниченных мобильных условиях. (Chrome DevTools: Lighthouse) 
Результаты могут меняться из-за устройства, фоновых процессов, маршрута сети, 
расширений браузера и динамического содержимого. Документация Lighthouse прямо 
предупреждает о вариативности Performance score. Поэтому сравнивать нужно запуски с 
одной конфигурацией и по возможности в чистом окне Chrome без расширений. (Chrome 
for Developers: Lighthouse performance scoring) 
В этой лабораторной работе выполняются три запуска до и три после изменений. Для 
таблицы используется медиана трёх значений. Это методика курса для уменьшения 
влияния случайного запуска, а не официальный проходной балл Lighthouse. 
Для анализа запускают production-сборку: 
npm run lint 
npm run build 
npm run start 
Проверка development-сервера и production-сервера отвечает разным задачам. Итоговые 
показатели Lighthouse фиксируются для production-версии на одном компьютере и в 
одинаковых условиях.

4.11 Core Web Vitals и лабораторные метрики 
Core Web Vitals — подмножество Web Vitals для оценки реального пользовательского 
опыта. Актуальный набор включает LCP, INP и CLS. Официальные рекомендуемые 
границы для хорошего пользовательского опыта: LCP не более 2,5 секунды, INP не более 
200 миллисекунд и CLS не более 0,1 для 75-го процентиля загрузок отдельно на 
мобильных и desktop-устройствах. (web.dev: Web Vitals) 
 LCP характеризует скорость появления крупнейшего видимого элемента содержимого; 
 INP характеризует отзывчивость страницы на взаимодействия; 
 CLS характеризует визуальную стабильность и неожиданные сдвиги макета. 
Необходимо различать лабораторные и полевые данные. Lighthouse загружает страницу в 
моделируемой среде без реального пользовательского ввода, поэтому не измеряет INP 
напрямую. В лаборатории для поиска потенциальных проблем отзывчивости используется 
TBT как proxy-метрика. LCP и CLS доступны в Lighthouse. Полевые значения зависят от 
реальных устройств, сетей и взаимодействий и не заменяются одним локальным аудитом. 
(web.dev: Web Vitals) 
4.12 Автоматическая и ручная проверка 
Автоматическая Accessibility-проверка быстро обнаруживает часть проблем: например, 
отсутствующее alt, некоторые ошибки ARIA и контраст. Официальный курс web.dev 
подчёркивает, что автоматические инструменты не находят все проблемы и могут 
требовать дополнения ручными и assistive technology тестами. (web.dev: Automated 
accessibility testing; Manual accessibility testing) 
После Lighthouse студент вручную проверяет: 
 последовательность Tab и Shift + Tab; 
 видимость фокуса; 
 закрытие меню и модального окна клавишей Escape; 
 возврат фокуса; 
 смысл alt, а не только его наличие; 
 отсутствие потери содержимого при масштабе 200%; 
 ориентацию portrait и landscape; 
 работу мышью, клавиатурой и сенсорным вводом; 
 читаемость текста поверх изображений и фонов. 
Lighthouse является инструментом контроля и диагностики, но высокий балл не 
подтверждает полное соответствие всем требованиям доступности, производительности 
или безопасности.

Проверьте окно с коротким и длинным содержимым, в portrait и landscape, а также при 
масштабе 200%. 
 
 
\n11 
Этап 6. Адаптивное бургер-меню 
На телефоне панель меню может занимать всю ширину, а на широком экране 
ограничивается max-width. Высота панели должна учитывать 100dvh, а при нехватке 
высоты содержимое прокручивается. 
Не удаляйте aria-expanded, aria-controls, role, aria-modal, управление Tab, Shift + Tab и 
Escape. Проверьте гостевое и пользовательское состояния. 
 
 
Этап 7. Адаптивная карта 
Задайте высоту карты через clamp() и уменьшите скругление на узком экране. Добавьте 
ResizeObserver после создания карты. В callback вызывайте map.container.fitToViewport(). 
В cleanup отключите observer и уничтожьте карту. 
Проверьте, что изменение ширины окна, открытие DevTools и поворот эмулируемого 
устройства не оставляют серых областей внутри карты. 
Этап 8. Hover, pointer и reduced motion 
Перенесите декоративный hover карточки в условие (hover: hover) and (pointer: fine). 
Сенсорный интерфейс не должен зависеть от hover. 
Добавьте prefers-reduced-motion: reduce и отключите необязательные переходы и 
анимации. Функциональные изменения состояния должны сохраняться.

8. Адаптивность карты 
Дополните тип карты: 
// Дополняет тип карты методом пересчёта размеров контейнера. 
 
type YandexMap = { 
  container: { 
    fitToViewport: () => void; 
  }; 
  geoObjects: { 
    add: (placemark: YandexPlacemark) => void; 
  }; 
  destroy: () => void; 
}; \n25 
В эффекте создания карты добавьте observer. Переменные объявляются рядом с map: 
// Хранит ссылки на карту, наблюдатель размеров и признак завершения эффекта. 
 
let disposed = false; 
let map: YandexMap | null = null; 
let resizeObserver: ResizeObserver | null = null; 
После создания map и добавления меток: 
// Следит за размером контейнера и уведомляет карту об изменении viewport. 
 
if (containerRef.current && typeof ResizeObserver !== "undefined") { 
  // Создаём наблюдатель за изменением размеров контейнера. 
  resizeObserver = new ResizeObserver(() => { 
    // Просим API карты пересчитать доступную область. 
    map?.container.fitToViewport(); 
  }); 
  // Начинаем наблюдение за DOM-контейнером карты. 
  resizeObserver.observe(containerRef.current); 
} 
Обновите cleanup: 
// Освобождает наблюдатель и экземпляр карты при размонтировании компонента. 
 
// В cleanup освобождаем подписки и внешние ресурсы эффекта. 
return () => { 
  disposed = true; 
  // Отключаем наблюдатель размеров. 
  resizeObserver?.disconnect(); 
  // Уничтожаем экземпляр карты и его обработчики. 
  map?.destroy(); 
}; 
Observer создаётся после карты. Не создавайте его на каждом рендере вне useEffect.
