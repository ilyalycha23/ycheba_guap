Теоретическая часть 
4.1 PostgreSQL как сервер реляционной базы данных 
PostgreSQL — объектно-реляционная система управления базами данных с открытым 
исходным кодом. Серверный процесс принимает подключения клиентских приложений, 
управляет файлами данных, выполняет SQL-команды и обеспечивает согласованность 
данных. Один запущенный сервер PostgreSQL может обслуживать несколько баз данных. 
Официальное введение рекомендует использовать отдельную базу для отдельного проекта 
или пользователя. (PostgreSQL: Architectural Fundamentals; Creating a Database) 
В этой работе необходимо различать: 
 сервер PostgreSQL — запущенная служба, которая слушает сетевой порт; 
 кластер баз данных — набор баз, которыми управляет один экземпляр сервера; 
 база данных study_space — логическое пространство данных учебного проекта; 
 схема public — пространство имён объектов внутри базы; 
 роль study_app — учётная запись PostgreSQL, от имени которой подключается 
приложение; 
 клиент psql — терминальная программа для отправки SQL-команд серверу. 
Наличие установленного pgAdmin не заменяет сервер PostgreSQL. pgAdmin является 
графическим клиентом, а хранение и обработку данных выполняет сервер. 
4.2 Установка PostgreSQL в Windows 
Официальная страница PostgreSQL для Windows направляет пользователя к 
интерактивному установщику EDB. В состав установщика входят сервер PostgreSQL, 
pgAdmin и StackBuilder. Для лабораторной работы обязательны сервер и командные 
инструменты; pgAdmin можно установить как дополнительный клиент. (PostgreSQL: 
Windows installers) 
Во время установки задаются каталог программы, каталог данных, пароль 
административной роли postgres, порт и локаль. Обычно используется порт 5432, но 
документация psql указывает, что фактический порт может быть другим и задаётся 
параметром -p. Выбранные значения необходимо записать: без них невозможно 
однозначно диагностировать ошибку подключения. \n3 
 
Пароль роли postgres является локальным административным секретом. Его нельзя 
помещать в отчёт, исходный код или снимок экрана. В отчёте пароль закрывается или не 
попадает в кадр. 
4.3 Роли, владельцы и принцип минимальных 
привилегий 
PostgreSQL использует роли для управления доступом. CREATE ROLE создаёт роль, а 
атрибут LOGIN разрешает ей подключаться к серверу. Роль может быть владельцем базы 
и объектов. (PostgreSQL: CREATE ROLE) 
Next.js-приложение не должно подключаться как postgres: административная роль имеет 
избыточные права. Для StudySpace создаётся отдельная роль study_app, которой 
принадлежит только учебная база. Такой подход уменьшает область последствий ошибки 
приложения и делает конфигурацию проекта явной. 
В лабораторной работе роль study_app не получает SUPERUSER, CREATEDB и 
CREATEROLE. База study_space создаётся владельцем study_app. Это учебная реализация 
принципа минимально необходимых прав. 
4.4 База данных и схема 
Команда CREATE DATABASE создаёт новую базу. Официальная документация отмечает, 
что имя базы должно быть уникальным внутри сервера, а выполнение требует 
соответствующего права. (PostgreSQL: CREATE DATABASE; Creating a Database) 
Строка подключения будет содержать имя базы study_space и параметр schema=public. 
База и схема — не одно и то же. Клиент сначала подключается к конкретной базе, а затем 
обращается к объектам схемы. В лабораторной работе используется стандартная схема 
public внутри отдельной базы. 
4.5 Терминальный клиент psql 
psql — терминальный клиент PostgreSQL. Он принимает SQL интерактивно, из файла или 
через аргумент -c. Для соединения используются параметры -h для хоста, -p для порта, -U 
для роли и -d для базы. (PostgreSQL: psql) 
# Подключаемся к локальной базе под прикладной ролью. 
psql -h localhost -p 5432 -U study_app -d study_space 
Внутри psql полезны метакоманды: 
 \conninfo — показывает текущее соединение; 
 \l — выводит базы данных; 
 \du — выводит роли; 
 \dn — выводит схемы; 
 \dt — выводит таблицы текущей схемы; 
 \q — завершает сеанс. \n4 
 
Метакоманды обрабатывает psql, поэтому они не являются SQL-командами и не 
заканчиваются точкой с запятой. 
4.6 Что такое ORM и из каких частей состоит Prisma 
ORM 
ORM связывает объекты прикладного кода с записями реляционной базы. Prisma ORM 
предоставляет схему данных, миграции и типобезопасный клиент для Node.js и 
TypeScript. Официальная документация описывает Prisma ORM как набор средств с 
моделью данных, автоматизированными миграциями, типобезопасностью и 
автодополнением. (Prisma ORM: Overview) 
В учебном проекте используются следующие части: 
 Prisma Schema — файл schema.prisma с источником данных, генератором и моделями; 
 Prisma CLI — команды init, format, validate, generate, migrate и studio; 
 Prisma Client — сгенерированный TypeScript-клиент для запросов; 
 Prisma Migrate — история версионируемых изменений физической схемы; 
 Prisma Studio — графический интерфейс просмотра и редактирования данных 
разработки. 
Prisma не заменяет PostgreSQL. PostgreSQL хранит данные и выполняет запросы, а Prisma 
формирует запросы и типы на основе описанной модели. 
4.7 Структура schema.prisma 
Официальная документация Prisma выделяет три части схемы: datasource, generator и data 
model. datasource задаёт тип источника данных, generator — создаваемый клиент, а блоки 
model описывают прикладные сущности. (Prisma: Overview on Prisma Schema) 
// Указывает генератор Prisma Client, совместимый с Prisma ORM 6. 
generator client { 
  provider = "prisma-client-js" 
} 
 
// Подключает локальную базу PostgreSQL через переменную окружения. 
datasource db { 
  provider = "postgresql" 
  url      = env("DATABASE_URL") 
} 
В пятой работе добавляется временная модель SetupCheck только для проверки генерации 
типов. Команда migrate не выполняется, поэтому физическая таблица из неё не создаётся. 
В шестой работе временная модель будет удалена и заменена моделями предметной 
области. 
4.8 Строка подключения PostgreSQL \n5 
 
Prisma использует URL подключения. Для Prisma ORM 6 URL задаётся в datasource через 
env("DATABASE_URL"). Официальный формат PostgreSQL включает пользователя, 
пароль, хост, порт и имя базы. (Prisma: Connection URLs) 
postgresql://USER:PASSWORD@HOST:PORT/DATABASE?schema=SCHEMA 
Для локального проекта: 
DATABASE_URL="postgresql://study_app:CHANGE_ME@localhost:5432/study_space?sch
ema=public" 
Специальные символы в имени пользователя или пароле должны быть percent-encoded. 
Реальное значение DATABASE_URL хранится только в локальном .env. В репозиторий 
помещается .env.example с заполнителями. 
4.9 Переменные окружения и граница сервера 
Next.js загружает переменные окружения из файлов .env*. Переменная без префикса 
NEXT_PUBLIC_ доступна серверному коду, но не встраивается в клиентский JavaScript. 
Официальная документация Next.js также указывает, что шаблон create-next-app добавляет 
.env-файлы в .gitignore. (Next.js: Environment Variables) 
DATABASE_URL не должна иметь префикс NEXT_PUBLIC_. Она используется Prisma 
CLI и серверным кодом. Нельзя импортировать PrismaClient в файл с директивой "use 
client", иначе серверная зависимость и секретная конфигурация окажутся на неправильной 
стороне границы приложения. 
4.10 Генерация Prisma Client 
Команда prisma generate читает generator и модели schema.prisma и создаёт клиент. Типы 
методов клиента выводятся из моделей, поэтому после изменения схемы клиент следует 
сгенерировать повторно. (Prisma CLI: Reference; Prisma Schema Overview) 
Пакеты prisma и @prisma/client должны иметь одну версию. В курсе используется 6.19.2: 
# Устанавливаем CLI только для разработки. 
npm install -D prisma@6.19.2 tsx 
 
# Устанавливаем клиент и загрузку .env для отдельных TypeScript-скриптов. 
npm install @prisma/client@6.19.2 dotenv 
Фиксация версии является методическим решением курса. Она не означает, что более 
новые версии Prisma не существуют; их миграционные руководства необходимо изучать 
отдельно. 
4.11 PrismaClient и горячая перезагрузка Next.js 
Prisma рекомендует избегать создания множества экземпляров PrismaClient при горячей 
перезагрузке Next.js. В режиме разработки модуль может загружаться повторно, поэтому 
экземпляр сохраняют в globalThis. В production создаётся обычный экземпляр. (Prisma: 
Next.js troubleshooting) \n6 
 
// Переиспользуем клиент между горячими перезагрузками development-сервера. 
const globalForPrisma = globalThis as unknown as { 
  prisma: PrismaClient | undefined; 
}; 
Один экземпляр клиента не означает одно SQL-соединение навсегда: Prisma управляет 
соединениями внутри клиента. Важное требование — не создавать новый PrismaClient при 
каждом запросе. 
4.12 Миграции и граница пятой работы 
Prisma Migrate создаёт и применяет версионируемые SQL-миграции. Документация Prisma 
различает migrate dev для разработки и migrate deploy для применения уже созданных 
миграций в production. migrate dev не должен использоваться как production-команда. 
(Prisma: Development and production) 
В лабораторной работе № 5 миграция не создаётся: физические таблицы проектируются в 
лабораторной работе № 6. На этом этапе проверяются только установка, конфигурация, 
генерация клиента и соединение. Команды db push, migrate dev, migrate reset и ручное 
создание таблиц выполнять нельзя.

Зафиксируйте без секретов:

 каталог установки; 
 каталог данных; 
 выбранный порт; 
 установлены ли Command Line Tools и pgAdmin; 
 имя службы PostgreSQL. \n7 
 
Не показывайте пароль роли postgres в отчёте. 
 
Этап 3. Проверка сервера и psql 
Откройте новый PowerShell после установки и выполните: 
# Проверяем доступность клиентской программы. 
psql --version 
 
# Подключаемся к служебной базе под административной ролью. 
psql -h localhost -p 5432 -U postgres -d postgres 
Если psql не найден, используйте SQL Shell (psql) из меню Пуск или добавьте каталог bin 
установленного PostgreSQL в пользовательский PATH. Не копируйте путь другой версии 
без проверки собственного каталога. 
В psql выполните SELECT version(); и \conninfo, затем завершите сеанс командой \q. 
\n8 
 
 
Этап 4. Создание роли и базы проекта 
Снова подключитесь к базе postgres под ролью postgres и выполните команды из 
приложения. Замените пароль на собственный локальный пароль, который не 
используется в других системах. 
-- Создаём отдельную роль, от имени которой будет работать StudySpace. 
CREATE ROLE study_app 
  WITH LOGIN 
  PASSWORD 'CHANGE_ME'; 
 
-- Создаём отдельную базу и назначаем прикладную роль владельцем. 
CREATE DATABASE study_space 
  WITH OWNER = study_app 
       ENCODING = 'UTF8'; 
Повторный запуск CREATE ROLE или CREATE DATABASE приведёт к ошибке 
существующего объекта. Не удаляйте чужие роли или базы; сначала проверьте \du и \l. 
Этап 5. Проверка прикладного подключения 
Подключитесь уже не как postgres, а как study_app: 
# Проверяем, что прикладная роль входит именно в учебную базу. 
psql -h localhost -p 5432 -U study_app -d study_space 
Выполните: 
-- Показываем фактическую базу, роль и серверный порт. 
SELECT current_database(), current_user, inet_server_port(); 
Результат должен содержать study_space и study_app. Команда \dt на этом этапе сообщает, 
что отношений нет: таблицы появятся в следующей работе. 
\n9 
 
Этап 6. Установка Prisma ORM 
В корне Next.js-проекта выполните: 
# Устанавливаем согласованные версии CLI, клиента и запуска TypeScript-
скриптов. 
npm install -D prisma@6.19.2 tsx 
npm install @prisma/client@6.19.2 dotenv 
 
# Проверяем фактически установленные версии. 
npx prisma --version 
В отчёте версии prisma и @prisma/client должны совпадать. 
Этап 7. Инициализация Prisma 
Выполните: 
# Создаём каталог prisma, schema.prisma и шаблон переменной подключения. 
npx prisma init --datasource-provider postgresql 
Проверьте появление prisma/schema.prisma и .env. Если эти файлы уже существуют, не 
запускайте init повторно и не перезаписывайте их: сравните содержимое с приложением. 
Этап 8. Настройка DATABASE_URL 
В .env укажите собственный пароль роли study_app: 
# Хранит локальное подключение к базе; реальный пароль не публикуется. 
DATABASE_URL="postgresql://study_app:CHANGE_ME@localhost:5432/study_space?sch
ema=public" 
Создайте .env.example с тем же ключом и заполнителем. Проверьте .gitignore. Выполните 
git status и убедитесь, что .env не предлагается к коммиту. 
Этап 9. Настройка schema.prisma 
Добавьте generator, datasource и временную модель SetupCheck из приложения. Эта модель 
нужна только для генерации типизированного клиента. Не запускайте миграцию. 
Выполните: 
# Форматируем и проверяем синтаксис Prisma Schema. 
npx prisma format 
npx prisma validate 
 
# Создаём типизированный Prisma Client. 
npx prisma generate 
Этап 10. Единственный экземпляр PrismaClient \n10 
 
Создайте app/lib/prisma.ts по приложению. Файл относится только к серверной части и не 
должен содержать директиву "use client". 
Этап 11. Диагностический запрос из TypeScript 
Создайте scripts/check-prisma.ts и выполните: 
# Запускаем серверный TypeScript-скрипт с реальным подключением. 
npx tsx scripts/check-prisma.ts 
Скрипт должен вывести study_space и study_app, а затем корректно вызвать 
prisma.$disconnect(). Если появляется P1000, проверьте имя роли и пароль. При P1001 
проверьте службу, хост и порт. Не публикуйте полный DATABASE_URL в сообщении об 
ошибке. 
Этап 12. Итоговая проверка 
Выполните: 
# Проверяем конфигурацию и приложение после подключения Prisma. 
npx prisma validate 
npx prisma generate 
npm run lint 
npm run build

Файл app/lib/prisma.ts 
// Создаёт единый серверный экземпляр PrismaClient для Next.js. 
 
import { PrismaClient } from "@prisma/client"; 
 
// Расширяем тип globalThis полем, используемым только в development. 
const globalForPrisma = globalThis as unknown as { 
  prisma: PrismaClient | undefined; 
}; 
 
// Переиспользуем клиент после горячей перезагрузки или создаём его впервые. 
export const prisma = globalForPrisma.prisma ?? new PrismaClient(); 
 
// Сохраняем экземпляр глобально только вне production. 
if (process.env.NODE_ENV !== "production") { 
  globalForPrisma.prisma = prisma; 
} 
8. Файл scripts/check-prisma.ts 
// Проверяет соединение Prisma с PostgreSQL без создания предметных таблиц. 
 
import "dotenv/config"; 
import { prisma } from "../app/lib/prisma"; 
 
// Описываем форму строки, которую возвращает диагностический SELECT. 
type ConnectionInfo = { 
  database: string; 
  role: string; 
  port: number; 
}; 
 
async function main() { \n16 
 
  // Запрашиваем у сервера фактические параметры текущего соединения. 
  const rows = await prisma.$queryRaw<ConnectionInfo[]>` 
    SELECT 
      current_database() AS database, 
      current_user AS role, 
      inet_server_port() AS port 
  `; 
 
  // Выводим только безопасные диагностические сведения, без DATABASE_URL. 
  console.log("Prisma connected:", rows[0]); 
} 
 
// Завершаем процесс с ненулевым кодом при ошибке подключения. 
main() 
  .catch((error) => { 
    console.error("Prisma connection failed:", error); 
    process.exitCode = 1; 
  }) 
  .finally(async () => { 
    // Освобождаем ресурсы отдельного диагностического скрипта. 
    await prisma.$disconnect(); 
  });
