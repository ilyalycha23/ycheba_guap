1. Место работы в курсе 
В лабораторной работе № 5 студент установил PostgreSQL, создал роль study_app и базу

В шестой работе логическая предметная область переводится в физическую схему

В TheraCity используются более многочисленные сущности, но StudySpace не копирует их 
названия или данные. Аналогия состоит в последовательности: Prisma Schema → 
миграция → seed → Prisma Client → серверная проверка пользователя → защищённая 
операция.

4. Теоретическая часть 
4.1 Физическая модель реляционной базы 
Физическая реализация переводит понятия предметной области в конкретные таблицы, 
столбцы, типы, ключи, ограничения и индексы PostgreSQL. Prisma Schema описывает 
модели приложения, а Prisma Migrate создаёт SQL, который изменяет фактическую схему 
базы. Официальная документация Prisma указывает, что модели соответствуют сущностям 
приложения, а скалярные поля моделей соответствуют столбцам реляционной базы. 
(Prisma: Models) 
В StudySpace создаются три таблицы: 
 User — зарегистрированные пользователи; 
 StudyPlace — учебные места, которые показываются в галерее и на карте; 
 FavoritePlace — связи между пользователями и выбранными ими местами. 
Типы, размеры строк и правила удаления в приложении являются проектными решениями 
курса. Их необходимо обосновать для собственной предметной области. 
4.2 Какие данные хранит каждая таблица 
User хранит: 
 id — стабильный UUID пользователя; 
 name — отображаемое имя; 
 email — нормализованный адрес для входа, уникальный в базе; 
 passwordHash — результат хеширования пароля, но не исходный пароль; 
 createdAt — время создания учётной записи; 
 updatedAt — время последнего изменения строки. \n3 
 
StudyPlace хранит: 
 id — UUID учебного места; 
 slug — уникальный читаемый идентификатор маршрута или данных; 
 title — название; 
 summary — краткое описание; 
 address — адрес или описание расположения; 
 image — путь к изображению из public; 
 imageAlt — альтернативный текст изображения; 
 latitude и longitude — координаты для карты; 
 createdAt и updatedAt — временные метки. 
FavoritePlace хранит: 
 userId — внешний ключ на User; 
 placeId — внешний ключ на StudyPlace; 
 createdAt — время добавления в избранное. 
Таблица FavoritePlace является явной таблицей связи многие-ко-многим. Составной 
первичный ключ (userId, placeId) не позволяет одному пользователю добавить одно место 
дважды. 
4.3 Первичные, уникальные и внешние ключи 
Документация PostgreSQL определяет первичный ключ как уникальный и не 
допускающий NULL идентификатор строки. Добавление первичного ключа также создаёт 
уникальный B-tree индекс. Уникальное ограничение обеспечивает уникальность значения 
или комбинации значений. Внешний ключ требует, чтобы значение ссылалось на 
существующую строку другой таблицы, и тем самым поддерживает ссылочную 
целостность. (PostgreSQL: Constraints) 
В Prisma используются: 
// Назначает одиночный первичный ключ. 
id String @id @default(uuid()) @db.Uuid 
 
// Требует уникальный email. 
email String @unique 
 
// Назначает составной первичный ключ таблицы связи. 
@@id([userId, placeId]) 
Уникальная проверка в интерфейсе не заменяет ограничение базы: два параллельных 
запроса могут пройти предварительную проверку. Окончательная гарантия уникальности 
принадлежит базе данных. 
4.4 Связи Prisma и внешние ключи \n4 
 
Prisma описывает связь полями отношений и скалярным полем внешнего ключа. Поле 
relation существует на уровне Prisma Client, а userId или placeId существует как 
физический столбец. (Prisma: Relations) 
// Связывает строку избранного с существующим пользователем. 
user User @relation(fields: [userId], references: [id], onDelete: Cascade) 
PostgreSQL определяет CASCADE как автоматическое удаление зависимых строк при 
удалении родительской строки. Для FavoritePlace это уместно: связь избранного не имеет 
смысла без пользователя или места. Само удаление пользователя не должно удалять 
независимые учебные места. 
4.5 Выбор типов PostgreSQL 
PostgreSQL предоставляет числовые, строковые, логические, временные, UUID и другие 
типы. Prisma позволяет дополнить скалярный тип нативным типом базы через @db. 
(PostgreSQL: Data Types; Prisma Schema Reference) 
В работе используются: 
 @db.Uuid для идентификаторов; 
 @db.VarChar(n) для строк с осмысленной максимальной длиной; 
 @db.Text для описания переменной длины; 
 @db.Decimal(9, 6) для координат с фиксированной точностью; 
 @db.Timestamptz(3) для времени с часовым поясом. 
Decimal перед отправкой в JSON преобразуется в number или строку, поскольку объект 
Prisma Decimal не является обычным JSON-числом. Для координат лабораторного 
диапазона Number(place.latitude) достаточно; в финансовых расчётах такое 
преобразование может быть недопустимо. 
4.6 Индексы 
Индекс помогает находить строки без полного просмотра таблицы, но занимает место и 
добавляет работу при изменении данных. PostgreSQL автоматически создаёт индексы для 
первичных и уникальных ограничений, однако внешний ключ на ссылающейся стороне не 
получает индекс автоматически. Документация PostgreSQL отмечает, что индексировать 
такие столбцы часто полезно. (PostgreSQL: Constraints; Indexes) 
Составной первичный ключ FavoritePlace начинается с userId и хорошо поддерживает 
запрос «избранное пользователя». Дополнительный @@index([placeId]) нужен для 
обратного запроса «какие пользователи выбрали место» и для операций, связанных с 
удалением или анализом места. 
4.7 Миграции Prisma Migrate 
Миграция — версионируемое описание изменения физической схемы. В development 
команда prisma migrate dev сравнивает модель, историю миграций и базу, создаёт SQL-
миграцию, применяет её и обновляет таблицу _prisma_migrations. Документация \n5 
 
запрещает использовать migrate dev как production-команду; там применяют migrate 
deploy. (Prisma: Development and production) 
# Создаём и применяем первую migration в локальной development-базе. 
npx prisma migrate dev --name init_study_space 
Файл migration.sql является частью исходного кода. Его необходимо прочитать и 
сохранить. Ручное редактирование уже применённой миграции создаёт расхождение 
истории. 
4.8 Начальное заполнение базы 
Seeding создаёт данные, необходимые для запуска или проверки приложения. 
Официальная документация Prisma рекомендует seed для воспроизводимого заполнения 
development-базы. В Prisma ORM 6 команда задаётся в поле prisma.seed package.json и 
запускается через prisma db seed; после migrate reset seed также может выполняться 
автоматически. (Prisma: Seeding) 
Идемпотентный seed можно запускать повторно без создания дубликатов. Для 
уникальных полей используется upsert: существующая строка обновляется, 
отсутствующая создаётся. В StudySpace seed создаёт одного демонстрационного 
пользователя, три учебных места и одну строку избранного. 
4.9 CRUD и Prisma Client 
CRUD означает Create, Read, Update и Delete. Prisma Client предоставляет методы create, 
findUnique, findMany, update, delete, upsert и групповые операции. (Prisma: CRUD) 
Серверные маршруты используют: 
 user.create для регистрации; 
 user.findUnique для входа и проверки сессии; 
 favoritePlace.upsert для идемпотентного добавления; 
 favoritePlace.deleteMany для безопасного повторного удаления; 
 studyPlace.findMany в ЛР7 для выдачи галереи. 
В select следует перечислять только безопасные поля. Возврат всей строки User может 
случайно отправить passwordHash клиенту. 
4.10 Хеширование паролей 
Пароль нельзя хранить в исходном виде. Официальное руководство Next.js по 
авторизации показывает хеширование пароля перед записью пользователя и подчёркивает 
сложность собственной auth-реализации. В учебном проекте используется bcrypt с cost 
factor 12. (Next.js: Authentication) 
// Преобразуем пароль в необратимый хеш перед записью в User. 
const passwordHash = await hash(password, 12); \n6 
 
bcrypt включает соль в результат. При входе compare проверяет пароль относительно 
сохранённого хеша. Клиенту возвращается только общее сообщение «Неверный email или 
пароль», чтобы не раскрывать существование адреса. 
4.11 Аутентификация, сессия и авторизация 
Руководство Next.js разделяет три понятия: 
 аутентификация проверяет личность пользователя; 
 управление сессией сохраняет состояние входа между запросами; 
 авторизация решает, какие данные и действия доступны пользователю. 
В лабораторной работе регистрация и вход выполняют аутентификацию. Подписанный 
JWT в cookie хранит минимальный идентификатор сессии. Перед изменением избранного 
сервер проверяет подпись токена и существование пользователя в базе — это авторизация 
защищённой операции. 
Скрытие кнопки на клиенте не является авторизацией. Злоумышленник может отправить 
HTTP-запрос напрямую, поэтому проверка выполняется внутри Route Handler рядом с 
изменением данных. 
4.12 Подписанная cookie-сессия 
Официальная документация Next.js описывает stateless-сессию как подписанные или 
зашифрованные данные в cookie и рекомендует использовать библиотеку управления 
сессией, например jose. В payload следует хранить минимальные данные, а не пароль или 
лишнюю персональную информацию. (Next.js: Authentication) 
В StudySpace JWT содержит userId и name, подписывается алгоритмом HS256 секретом 
AUTH_SECRET и действует семь дней. Секрет хранится только на сервере. 
Cookie задаётся с атрибутами: 
 httpOnly — клиентский JavaScript не читает cookie; 
 secure — cookie передаётся только по HTTPS в production; 
 sameSite=lax — ограничивает часть межсайтовых отправок; 
 path=/ — cookie доступна маршрутам приложения; 
 maxAge — задаёт срок действия. 
Функция cookies в современных версиях Next.js асинхронна. Читать cookie можно в 
серверном коде, а устанавливать или удалять — в Server Function или Route Handler. 
(Next.js: cookies) 
4.13 Ограничения учебной auth-реализации 
Официальное руководство Next.js рекомендует для production использовать проверенную 
auth-библиотеку, поскольку готовое решение должно учитывать дополнительные угрозы и 
сценарии: восстановление доступа, подтверждение email, смену пароля, отзыв сессий, \n7 
 
ограничение частоты запросов, аудит, CSRF, MFA и безопасное управление ключами. 
(Next.js: Authentication) 
Реализация лабораторной работы предназначена для понимания потока данных и не 
объявляется полноценной production-системой. Stateless JWT нельзя отозвать до истечения 
срока без дополнительного механизма. Для более сложного проекта можно использовать 
database sessions или специализированную библиотеку.

// Подписывает, проверяет, устанавливает и удаляет учебную cookie-сессию. 
 
import { SignJWT, jwtVerify } from "jose"; 
import { cookies } from "next/headers"; 
 
const COOKIE_NAME = "study_session"; 
const SESSION_MAX_AGE = 60 * 60 * 24 * 7; 
 
// Читаем серверный секрет и сразу запрещаем запуск с пустым значением. 
function getSecret(): Uint8Array { 
  const value = process.env.AUTH_SECRET; 
  if (!value) { 
    throw new Error("AUTH_SECRET is not configured"); 
  } 
  return new TextEncoder().encode(value); 
} 
 
// Храним в сессии только минимальные данные пользователя. 
export type SessionPayload = { 
  userId: string; 
  name: string; 
}; 
 
// Создаём подписанный JWT с ограниченным сроком действия. 
async function signSession(payload: SessionPayload): Promise<string> { 
  return new SignJWT(payload) 
    .setProtectedHeader({ alg: "HS256" }) 
    .setIssuedAt() 
    .setExpirationTime("7d") 
    .sign(getSecret()); 
} 
 
// Устанавливаем cookie только из серверного Route Handler. 
export async function createSession(payload: SessionPayload): Promise<void> { 
  const token = await signSession(payload); 
  const store = await cookies(); 
 
  store.set(COOKIE_NAME, token, { 
    httpOnly: true, 
    secure: process.env.NODE_ENV === "production", 
    sameSite: "lax", 
    path: "/", 
    maxAge: SESSION_MAX_AGE, 
  }); 
} \n21 
 
 
// Возвращаем payload только после успешной проверки подписи и срока. 
export async function readSession(): Promise<SessionPayload | null> { 
  const token = (await cookies()).get(COOKIE_NAME)?.value; 
  if (!token) return null; 
 
  try { 
    const { payload } = await jwtVerify(token, getSecret(), { 
      algorithms: ["HS256"], 
    }); 
 
    if (typeof payload.userId !== "string" || typeof payload.name !== "string") { 
      return null; 
    } 
 
    return { userId: payload.userId, name: payload.name }; 
  } catch { 
    // Любая ошибка подписи, формата или срока превращает запрос в гостевой. 
    return null; 
  } 
} 
 
// Удаляем cookie при выходе пользователя. 
export async function deleteSession(): Promise<void> { 
  (await cookies()).delete(COOKIE_NAME); 
}

// Проверяет сессию и загружает актуального пользователя из базы. 
 
import { prisma } from "./prisma"; 
import { readSession } from "./auth"; 
 
export async function getCurrentUser() { 
  // Сначала проверяем подписанный идентификатор сессии. 
  const session = await readSession(); 
  if (!session) return null; 
 
  // Затем убеждаемся, что пользователь всё ещё существует в базе. 
  return prisma.user.findUnique({ 
    where: { id: session.userId }, 
    select: { 
      id: true, 
      name: true, 
      email: true, 
    }, 
  });

import { createSession } from "@/app/lib/auth"; 
import { prisma } from "@/app/lib/prisma"; 
import { validateRegistration } from "@/app/lib/validation"; 
 
export const runtime = "nodejs"; 
 
export async function POST(request: Request) { \n22 
 
  try { 
    // Читаем непроверенное тело запроса. 
    const body = await request.json(); 
    const validation = validateRegistration(body); 
 
    // Возвращаем ошибки клиента без обращения к базе. 
    if (!validation.data) { 
      return NextResponse.json( 
        { errors: validation.errors }, 
        { status: 400 }, 
      ); 
    } 
 
    const { name, email, password } = validation.data; 
 
    // Хешируем пароль до записи строки User. 
    const passwordHash = await hash(password, 12); 
 
    // Создаём пользователя и сразу выбираем только безопасные поля. 
    const user = await prisma.user.create({ 
      data: { name, email, passwordHash }, 
      select: { id: true, name: true, email: true }, 
    }); 
 
    // Сохраняем минимальные данные в подписанной cookie-сессии. 
    await createSession({ userId: user.id, name: user.name }); 
 
    return NextResponse.json({ user }, { status: 201 }); 
  } catch (error) {

    if ( 
      error instanceof Prisma.PrismaClientKnownRequestError && 
      error.code === "P2002"

      return NextResponse.json( 
        { errors: ["Этот email уже зарегистрирован"] }, 
        { status: 409 }, 
      ); 
    } 
 
    // Не отправляем клиенту внутренний объект ошибки или секреты. 
    return NextResponse.json( 
      { errors: ["Внутренняя ошибка сервера"] }, 
      { status: 500 }, 
    ); 
  }

// Проверяет email и пароль, затем создаёт сессию пользователя. 
 
import { compare } from "bcrypt"; 
import { NextResponse } from "next/server"; 
import { createSession } from "@/app/lib/auth"; 
import { prisma } from "@/app/lib/prisma"; 
import { normalizeEmail } from "@/app/lib/validation"; 
 
export const runtime = "nodejs"; 
 
export async function POST(request: Request) { 
  try { 
    // Нормализуем email и приводим пароль к строке. 
    const body = (await request.json()) as Record<string, unknown>; 
    const email = normalizeEmail(body.email); 
    const password = String(body.password ?? ""); \n23 
 
 
    if (!email || !password) { 
      return NextResponse.json( 
        { errors: ["Заполните email и пароль"] }, 
        { status: 400 }, 
      ); 
    } 
 
    // Для проверки пароля временно загружаем passwordHash только на сервере. 
    const account = await prisma.user.findUnique({ where: { email } }); 
 
    // Используем одно сообщение для отсутствующего аккаунта и неверного пароля. 
    if (!account || !(await compare(password, account.passwordHash))) { 
      return NextResponse.json( 
        { errors: ["Неверный email или пароль"] }, 
        { status: 401 }, 
      ); 
    } 
 
    // Создаём подписанную сессию после успешной проверки. 
    await createSession({ userId: account.id, name: account.name }); 
 
    // Явно формируем DTO без passwordHash. 
    const user = { 
      id: account.id, 
      name: account.name, 
      email: account.email, 
    }; 
 
    return NextResponse.json({ user }); 
  } catch { 
    return NextResponse.json( 
      { errors: ["Внутренняя ошибка сервера"] }, 
      { status: 500 }, 
    ); 
  } 
}

// Защищает добавление и удаление избранного серверной проверкой пользователя. 
 
import { NextResponse } from "next/server"; 
import { getCurrentUser } from "@/app/lib/current-user"; 
import { prisma } from "@/app/lib/prisma"; 
 
type RouteParams = { 
  params: Promise<{ placeId: string }>; 
}; 
 
export async function POST(_request: Request, context: RouteParams) { 
  // Авторизуем действие рядом с изменением данных. 
  const user = await getCurrentUser(); 
  if (!user) { 
    return NextResponse.json({ error: "Unauthorized" }, { status: 401 }); 
  } 
 
  const { placeId } = await context.params; 
 
  // Не создаём связь с отсутствующим учебным местом. 
  const place = await prisma.studyPlace.findUnique({ 
    where: { id: placeId }, 
    select: { id: true }, 
  }); 
  if (!place) { 
    return NextResponse.json({ error: "Place not found" }, { status: 404 }); 
  } 
 
  // Upsert делает повторный POST идемпотентным для одной пары ключей. 
  const favorite = await prisma.favoritePlace.upsert({ 
    where: { userId_placeId: { userId: user.id, placeId } }, 
    update: {}, 
    create: { userId: user.id, placeId }, 
  }); 
 
  return NextResponse.json({ favorite }, { status: 201 }); 
} 
 
export async function DELETE(_request: Request, context: RouteParams) { 
  // Гость не может изменять строки FavoritePlace. 
  const user = await getCurrentUser(); 
  if (!user) { 
    return NextResponse.json({ error: "Unauthorized" }, { status: 401 }); 
  } 
 
  const { placeId } = await context.params; 
 
  // Удаляем только связь пользователя, полученного из проверенной сессии. 
  const result = await prisma.favoritePlace.deleteMany({ 
    where: { userId: user.id, placeId }, 
  }); 
 
  return NextResponse.json({ deleted: result.count }); 
}
