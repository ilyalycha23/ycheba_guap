1. Место работы в курсе 
К началу седьмой работы StudySpace содержит адаптивный интерфейс из ЛР1–ЛР4, 
локальный PostgreSQL и Prisma ORM из ЛР5, а также физические таблицы, seed и 
серверную авторизацию из ЛР6. Однако клиентские компоненты всё ещё могут читать 
статический массив, хранить избранное в useState и использовать DemoAuthProvider. 
В заключительной работе клиент переводится на реальные Route Handlers. Галерея 
получает StudyPlace из PostgreSQL, AuthProvider восстанавливает пользователя через 
/api/auth/me, формы регистрации и входа отправляют запросы серверу, а избранное 
сохраняется в FavoritePlace. После соединения выполняются проверки на трёх уровнях: 
ручные HTTP-сценарии, модульные тесты чистой логики с Vitest и сквозной 
пользовательский сценарий с Playwright. 
В TheraCity клиент и сервер соединены большим числом маршрутов и сущностей. 
StudySpace воспроизводит архитектурный принцип и методику тестирования на 
собственной предметной области, не копируя интерфейс, данные и бизнес-правила 
TheraCity.

4. Теоретическая часть 
4.1 Клиент-серверный поток данных 
В полном веб-приложении клиентский компонент не обращается напрямую к файлам 
PostgreSQL. Браузер отправляет HTTP-запрос Route Handler, сервер проверяет входные 
данные и пользователя, Prisma Client выполняет запрос к PostgreSQL, а сервер возвращает 
JSON-ответ. Клиент преобразует ответ в состояние React и обновляет интерфейс. 
Для StudySpace поток чтения выглядит так: 
PlacesGallery → GET /api/places → Prisma Client → PostgreSQL 
             ← JSON places + isFavorite ← 
Поток изменения избранного: 
кнопка → POST/DELETE /api/favorites/:placeId → проверка cookie и User 
       → upsert/deleteMany FavoritePlace → JSON → обновление карточки 
Названия маршрутов и форма DTO являются контрактом курса, а правила Request, 
Response и Route Handlers основаны на официальной документации. 
4.2 Route Handlers в App Router 
Route Handlers определяются файлом route.ts внутри app и используют Web Request и 
Response API. Next.js поддерживает GET, POST, PUT, PATCH, DELETE, HEAD и 
OPTIONS. Неподдерживаемый метод получает 405. Route Handlers доступны только в app 
и не должны находиться на одном сегменте с page.tsx. (Next.js: Route Handlers) 
// Возвращаем JSON из GET-обработчика. 
export async function GET() { 
  return Response.json({ ok: true }); 
} \n3 
 
GET Route Handler по умолчанию не кэшируется в актуальном App Router, но при чтении 
cookie маршрут в любом случае зависит от конкретного запроса. Для учебной ясности 
/api/places объявляется dynamic = "force-dynamic". 
4.3 HTTP-контракт и методы 
HTTP-метод выражает намерение запроса. В StudySpace используются: 
 GET — чтение мест и текущего пользователя; 
 POST — регистрация, вход, выход и добавление избранного; 
 DELETE — удаление избранного. 
Ответ включает status и JSON-тело. Успешный контракт курса: 
 200 OK — чтение, вход, выход или удаление; 
 201 Created — регистрация или создание связи избранного. 
Ошибки: 
 400 Bad Request — неверная форма входных данных; 
 401 Unauthorized — отсутствует подтверждённая сессия; 
 404 Not Found — место не существует; 
 409 Conflict — нарушена уникальность email; 
 500 Internal Server Error — непредвиденная серверная ошибка. 
Статусы не заменяют понятное безопасное сообщение, а сообщение не заменяет 
корректный статус. 
4.4 DTO и сериализация 
Data Transfer Object — объект, специально сформированный для передачи через границу 
сервера. Он не обязан повторять всю строку базы. Руководство Next.js по авторизации 
рекомендует возвращать только необходимые данные, чтобы чувствительные поля не 
попали клиенту. (Next.js: Authentication) 
UserDTO содержит id, name и email, но не passwordHash. StudyPlaceDTO содержит поля 
карточки, координаты number и вычисленный isFavorite. createdAt не отправляется, если 
интерфейс его не использует. 
Prisma Decimal преобразуется явно: 
// Преобразуем координаты в обычные JSON-числа для карты. 
latitude: Number(place.latitude), 
longitude: Number(place.longitude), 
Сервер вычисляет isFavorite на основе проверенного user.id. Клиент не может назначить 
чужой userId и не является источником истины для авторизации. 
4.5 Fetch API, JSON и cookie \n4 
 
Fetch API возвращает Promise объекта Response. Ошибочный HTTP-статус сам по себе не 
отклоняет Promise, поэтому клиент обязан проверить response.ok и прочитать тело. (MDN: 
Fetch API) 
// Проверяем статус до использования JSON как успешного результата. 
const response = await fetch("/api/places", { cache: "no-store" }); 
const payload = await response.json(); 
if (!response.ok) throw new Error("Не удалось загрузить места"); 
Для same-origin запроса cookie отправляются по умолчанию, но в учебном коде credentials: 
"same-origin" указывается явно. httpOnly cookie нельзя прочитать через document.cookie; 
браузер прикладывает её к запросу, а сервер читает через cookies(). 
4.6 Состояния асинхронного интерфейса 
Сетевой запрос не завершается мгновенно и может завершиться ошибкой или пустым 
результатом. Поэтому интерфейс должен различать: 
 loading — запрос выполняется; 
 success — данные получены; 
 empty — успешный ответ не содержит мест; 
 error — запрос или ответ завершился неуспешно. 
Показывать пустую сетку во всех четырёх случаях нельзя: пользователь не понимает, 
загружается ли страница, действительно ли данных нет или сервер недоступен. 
В useEffect создаётся AbortController. Cleanup отменяет запрос при размонтировании 
компонента и предотвращает обновление уже неактуального состояния. 
4.7 Синхронизация AuthProvider 
React Context работает только в Client Components. Руководство Next.js отмечает, что 
контекст не доступен Server Components; он подходит для клиентского состояния 
интерфейса, но серверные проверки всё равно должны выполняться рядом с источником 
данных. (Next.js: Authentication) 
AuthProvider хранит три состояния: 
 loading — GET /api/auth/me ещё выполняется; 
 authenticated — сервер вернул пользователя; 
 guest — сервер вернул user: null. 
Методы login и register сначала получают подтверждённый UserDTO от сервера, затем 
обновляют контекст. Метод logout удаляет cookie через Route Handler и очищает user. 
После перезагрузки refresh снова получает состояние с сервера. 
4.8 Пессимистичное и оптимистичное обновление \n5 
 
При пессимистичном обновлении клиент ждёт успешный ответ сервера и только затем 
меняет UI. При оптимистичном обновлении UI меняется сразу, а при ошибке выполняется 
откат. 
В лабораторной работе избранное обновляется пессимистично. Этот вариант проще 
проверять: кнопка блокируется, запрос завершается, сервер подтверждает изменение, 
после чего isFavorite меняется. Для улучшения ощущения скорости можно перейти на 
оптимистичную модель, но тогда обязательны откат, защита от повторных кликов и 
обработка конфликтов. 
4.9 Авторизация остаётся серверной 
Клиент может скрыть кнопку для гостя, но защищённый Route Handler всё равно вызывает 
getCurrentUser. Официальное руководство Next.js рекомендует проверять авторизацию 
перед изменением данных и располагать безопасные проверки близко к источнику 
данных. (Next.js: Authentication) 
Сервер использует user.id из проверенной cookie-сессии. Поле userId не принимается из 
JSON или URL. Это предотвращает изменение FavoritePlace другого пользователя через 
подмену клиентского запроса. 
4.10 Виды тестирования 
Официальное руководство Next.js различает: 
 unit testing — отдельная функция или небольшой блок в изоляции; 
 component testing — поведение компонента и его props; 
 integration testing — совместная работа нескольких частей; 
 end-to-end testing — пользовательский сценарий в браузере, близком к реальному; 
 snapshot testing — сравнение вывода со снимком. (Next.js: Testing) 
В работе чистые функции normalizeEmail и validateRegistration тестируются модульно. 
Полный путь «страница → Route Handler → Prisma → PostgreSQL → cookie → страница» 
проверяется Playwright. Next.js рекомендует E2E-тестирование вместо unit-тестирования 
async Server Components, поддержка которых тестовыми инструментами может быть 
ограничена. 
4.11 Vitest 
Vitest — тестовый фреймворк, который поддерживает TypeScript и ищет файлы .test. или 
.spec. По официальной документации test задаёт проверку, а expect формулирует 
ожидаемый результат. Команда vitest run выполняет тесты один раз, что удобно для 
итоговой проверки. (Vitest: Getting Started; Writing Tests) 
Модульные тесты должны быть детерминированными: они не зависят от PostgreSQL, 
времени, сети и порядка запуска. Поэтому в них проверяется чистая валидация, а не 
реальная регистрация. 
4.12 Playwright \n6 
 
Playwright запускает браузер и автоматизирует пользовательские действия. Конфигурация 
webServer может запустить локальный сервер перед тестами, а baseURL позволяет 
использовать относительные адреса. reuseExistingServer обычно разрешают локально и 
отключают в CI. (Playwright: Web server) 
Для более близкой к production проверки сначала выполняется npm run build, а Playwright 
запускает npm run start. Тест использует доступные селекторы getByRole и getByLabel 
вместо нестабильных CSS-классов. 
4.13 Тестовые данные и изоляция 
Тест не должен зависеть от заранее свободного email. Он создаёт адрес с Date.now(), а 
afterAll удаляет тестового пользователя. Внешние ключи FavoritePlace с onDelete: Cascade 
удаляют зависимые связи автоматически. 
Для командного или production-проекта следует использовать отдельную test-базу и 
воспроизводимую миграцию. В учебной локальной работе допускается development-база 
при обязательной очистке. Нельзя запускать тест, который удаляет все строки или 
сбрасывает базу без точной проверки окружения. 
4.14 Итоговая стратегия проверки 
Один вид теста не заменяет остальные: 
 prisma validate и migrate status проверяют конфигурацию и историю схемы; 
 lint проверяет правила статического анализа; 
 unit tests быстро проверяют чистую логику; 
 build проверяет типы и production-сборку Next.js; 
 e2e проверяет реальный пользовательский поток; 
 ручная проверка дополняет автоматизацию картой, модальным окном, адаптивностью 
и доступностью. 
Проходящий E2E-сценарий не доказывает отсутствие всех ошибок безопасности. Тест 
подтверждает только сформулированный сценарий и ожидаемые проверки.

import { NextResponse } from "next/server";

// Ответ зависит от cookie текущего запроса и не является общим кэшем. 
export const dynamic = "force-dynamic"; 
 
export async function GET() { 
  try { 
    // Гость получает места без персональных связей. 
    const user = await getCurrentUser(); 
 
    // Читаем предметные данные и только нужные favorite placeId. 
    const [places, favorites] = await Promise.all([ 
      prisma.studyPlace.findMany({ orderBy: { title: "asc" } }), 
      user 
        ? prisma.favoritePlace.findMany({ 
            where: { userId: user.id }, 
            select: { placeId: true }, 
          }) 
        : Promise.resolve([]), 
    ]); 
 
    // Set обеспечивает быструю проверку каждого места. 
    const favoriteIds = new Set(favorites.map((item) => item.placeId)); 
 
    // Формируем стабильный DTO без внутренних временных полей. 
    const result = places.map((place) => ({ 
      id: place.id, 
      slug: place.slug, 
      title: place.title, \n17 
 
      summary: place.summary, 
      address: place.address, 
      image: place.image, 
      imageAlt: place.imageAlt, 
      latitude: Number(place.latitude), 
      longitude: Number(place.longitude), 
      isFavorite: favoriteIds.has(place.id), 
    })); 
 
    return NextResponse.json({ places: result }); 
  } catch { 
    // Не раскрываем клиенту объект ошибки подключения или DATABASE_URL. 
    return NextResponse.json(

// Синхронизирует клиентский интерфейс с серверной cookie-сессией. 
 
"use client"; 
 
import { 
  createContext, 
  useCallback, 
  useContext, 
  useEffect, 
  useMemo, 
  useState, 
  type ReactNode, 
} from "react"; 
 
export type UserDTO = { 
  id: string; 
  name: string; 
  email: string; 
}; 
 
type AuthStatus = "loading" | "authenticated" | "guest"; 
 
type AuthContextValue = { 
  user: UserDTO | null; 
  status: AuthStatus; 
  refresh: () => Promise<void>; 
  login: (email: string, password: string) => Promise<void>; 
  register: (input: { 
    name: string; 
    email: string; 
    password: string; 
    confirmPassword: string; 
  }) => Promise<void>; 
  logout: () => Promise<void>; 
}; 
 
const AuthContext = createContext<AuthContextValue | null>(null); 
 
// Читаем безопасное сообщение из согласованного JSON-ответа. 
async function readError(response: Response): Promise<string> { 
  const payload = (await response.json().catch(() => null)) as 
    | { error?: string; errors?: string[] } 
    | null; 
 
  return payload?.errors?.[0] ?? payload?.error ?? "Ошибка запроса"; \n18 
 
} 
 
export default function AuthProvider({ children }: { children: ReactNode }) { 
  const [user, setUser] = useState<UserDTO | null>(null); 
  const [status, setStatus] = useState<AuthStatus>("loading"); 
 
  // Восстанавливаем состояние из серверной cookie, не читая её на клиенте. 
  const fetchCurrentUser = useCallback(async (): Promise<UserDTO | null> => { 
    const response = await fetch("/api/auth/me", { 
      cache: "no-store", 
      credentials: "same-origin", 
    }); 
   
    if (!response.ok) { 
      return null; 
    } 
   
    const payload = (await response.json()) as { user: UserDTO | null }; 
    return payload.user; 
  }, []); 
 
  const refresh = useCallback(async () => { 
    const currentUser = await fetchCurrentUser(); 
   
    setUser(currentUser); 
    setStatus(currentUser ? "authenticated" : "guest"); 
  }, [fetchCurrentUser]); 
 
  useEffect(() => { 
    void fetchCurrentUser().then((currentUser) => { 
      setUser(currentUser); 
      setStatus(currentUser ? "authenticated" : "guest"); 
    }); 
  }, [fetchCurrentUser]); 
 
  const login = useCallback(async (email: string, password: string) => { 
    const response = await fetch("/api/auth/login", { 
      method: "POST", 
      headers: { "Content-Type": "application/json" }, 
      credentials: "same-origin", 
      body: JSON.stringify({ email, password }), 
    }); 
 
    if (!response.ok) throw new Error(await readError(response)); 
 
    const payload = (await response.json()) as { user: UserDTO }; 
    setUser(payload.user); 
    setStatus("authenticated"); 
  }, []); 
 
  const register = useCallback(async (input: { 
    name: string; 
    email: string; 
    password: string; 
    confirmPassword: string; 
  }) => { 
    const response = await fetch("/api/auth/register", { 
      method: "POST", 
      headers: { "Content-Type": "application/json" }, 
      credentials: "same-origin", 
      body: JSON.stringify(input), 
    }); 
 
    if (!response.ok) throw new Error(await readError(response)); 
 
    const payload = (await response.json()) as { user: UserDTO }; 
    setUser(payload.user); 
    setStatus("authenticated"); \n19 
 
  }, []); 
 
  const logout = useCallback(async () => { 
    const response = await fetch("/api/auth/logout", { 
      method: "POST", 
      credentials: "same-origin", 
    }); 
 
    if (!response.ok) throw new Error(await readError(response)); 
    setUser(null); 
    setStatus("guest"); 
  }, []); 
 
  // Стабилизируем объект контекста для дочерних Client Components. 
  const value = useMemo( 
    () => ({ user, status, refresh, login, register, logout }), 
    [user, status, refresh, login, register, logout], 
  ); 
 
  return <AuthContext.Provider value={value}>{children}</AuthContext.Provider>; 
} 
 
export function useAuth(): AuthContextValue { 
  const value = useContext(AuthContext); 
  if (!value) throw new Error("useAuth must be used inside AuthProvider"); 
  return value; 
}

        credentials: "same-origin", 
      }); 
 
      if (response.status === 401) { 
        // Синхронизируем UI, если сервер больше не принимает сессию. 
        await refresh(); 
        throw new Error("Сеанс завершён. Выполните вход снова."); 
      } 
 
      if (!response.ok) throw new Error("Не удалось изменить избранное"); 
 
      // Меняем только карточку, изменение которой подтвердил сервер. 
      setPlaces((current) => 
        current.map((item) => 
          item.id === place.id 
            ? { ...item, isFavorite: !item.isFavorite } 
            : item, 
        ), 
      ); 
    } catch (value) { 
      setError(value instanceof Error ? value.message : "Ошибка избранного"); 
    } finally { 
      setPendingId(null); 
    } 
  } 
 
  if (loading) return <p role="status">Загрузка учебных мест…</p>; 
 
  if (error && places.length === 0) { 
    return ( 
      <div role="alert"> 
        <p>{error}</p> 
        <button type="button" onClick={retry}>Повторить</button> 
      </div> 
    ); \n24 
 
  } 
 
  if (places.length === 0) return <p>Учебные места пока не добавлены.</p>; 
 
  return ( 
    <> 
      {error ? <p role="alert">{error}</p> : null} 
 
      <div className={styles.grid}> 
        {places.map((place) => ( 
          <article className={styles.card} key={place.id}> 
            <div className={styles.imageWrap}> 
              <Image 
                src={place.image} 
                alt={place.imageAlt} 
                fill 
                sizes="(max-width: 48rem) 100vw, 33vw" 
                className={styles.image} 
              /> 
            </div> 
 
            <h2 className={styles.title}>{place.title}</h2> 
            <p className={styles.summary}>{place.summary}</p> 
 
            {status === "authenticated" ? ( 
              <button 
                type="button" 
                disabled={pendingId === place.id} 
                aria-pressed={place.isFavorite} 
                aria-label={`${ 
                  place.isFavorite 
                    ? "Удалить из избранного" 
                    : "Добавить в избранное" 
                }: ${place.title}`} 
                onClick={() => void toggleFavorite(place)} 
              > 
                {place.isFavorite ? "В избранном" : "В избранное"} 
              </button> 
            ) : ( 
              <Link href="/auth/login">Войдите, чтобы добавить в избранное</Link> 
            )} 
          </article> 
        ))} 
      </div> 
 
      {/* Передайте places в PhotoMap и выбранный объект в PhotoModal из ЛР3. */} 
    </> 
  ); 
}
