Лабораторная работа №6 (лаба6) — подробный ход работы
Методичка: глава 6, п. 6.4 (основное задание), с опорой на п. 6.1 (управляющие конструкции) и п. 6.3 (функции). Вариант 12. СУБД: PostgreSQL 11+ (нужны CREATE PROCEDURE и CALL).

══════════════════════════════════════════════════════════════
Подготовка
══════════════════════════════════════════════════════════════

Перед любыми скриптами ЛР6 в базе должны существовать обычные учебные таблицы из первых лабораторных: типичная цепочка — выполнение lab1/01_schema.sql (создание всех таблиц и внешних ключей) и затем lab2/01_insert_test_data.sql (заполнение подразделений, должностей, штата, сотрудников, приёмов, детей и т.д.). Процедуры и функции ЛР6 не «рисуют» заново схему: они опираются на уже существующие отношения сотрудник, прием, должность и другие. Имена объектов ЛР6 начинаются с префикса lr6_, чтобы не пересекаться с системными и учебными именами.

Если вы уже запускали ЛР6 и хотите поставить объекты заново без ручного удаления, имеет смысл один раз выполнить lab6/09_drop_lr6_objects.sql — он снимает созданные в рамках лабораторной процедуры, функции и связанные объекты, после чего скрипты 01–08 можно выполнять снова.

══════════════════════════════════════════════════════════════
01_proc_insert_with_directory.sql — приём с «дозаполнением» справочника должностей
══════════════════════════════════════════════════════════════

Здесь создаётся хранимая процедура lr6_insert_hire_with_position на языке PL/pgSQL. Смысл учебного примера близок к жизненной ситуации: при оформлении приёма на работу внешняя система может передать идентификатор должности, которого ещё нет в справочнике. Вместо того чтобы заранее гарантировать наличие каждой должности в таблице должность, процедура сама проверяет справочник и при необходимости вставляет недостающую строку.

Сначала процедура проверяет, что указанный сотрудник и подразделение вообще существуют в базе. Если нет — вызывается RAISE EXCEPTION с подстановкой ид в текст сообщения: так вызывающий код или человек в psql сразу видит, какой параметр неверен, а не получает общую ошибку внешнего ключа от СУБД.

Дальше ключевой фрагмент: IF NOT EXISTS (SELECT 1 FROM должность WHERE ид = p_должность) — если строки с таким первичным ключом нет, выполняется INSERT в должность с переданным ид, искусственным наименованием вида «LR6 должность id …» и категорией «прочее». Так моделируется «подтянуть справочник под входящий код». После этого внешний ключ в таблице прием уже не «споткнётся» о пустой справочник.

Новый первичный ключ для строки приёма не передаётся снаружи: процедура читает COALESCE(MAX(ид),0)+1 из таблицы прием и кладёт результат в локальную переменную, затем вставляет одну строку в прием с этим ид и переданными параметрами. Это упрощённая схема нумерации; в промышленной системе часто используют SERIAL или SEQUENCE.

В отчёте имеет смысл описать словами цепочку «проверка сотрудника и подразделения → при необходимости вставка в должность → вычисление следующего ид приёма → вставка в прием», а в приложении показать CALL (например, с несуществующей должностью 90) и результат двух SELECT — по должность и по прием.

══════════════════════════════════════════════════════════════
02_proc_delete_employee_cascade.sql — «ручной» каскад при удалении сотрудника
══════════════════════════════════════════════════════════════

В учебной схеме на дочерние таблицы (перевод, увольнение, прием, дети) навешаны внешние ключи на сотрудник с политикой NO ACTION или аналогичной: удалить сотрудника «в лоб», пока на него ссылаются строки, нельзя. Процедура lr6_delete_employee инкапсулирует правильный порядок: сначала удаляются все зависимые строки в фиксированном порядке (перевод, увольнение, прием, дети), и только после этого удаляется сам сотрудник. Так демонстрируется то, что в других СУБД или при включённом ON DELETE CASCADE делает автоматика, — здесь же явно видно, какие таблицы затронуты.

Важно понимать последствия: CALL реально уничтожает данные. Для отчёта безопаснее использовать копию базы, тестовый ид сотрудника или сценарий с транзакцией и ROLLBACK из файла 10_demo_transaction.sql.

══════════════════════════════════════════════════════════════
03_proc_delete_subdivision_safe.sql — удаление только «листового» подразделения
══════════════════════════════════════════════════════════════

Процедура lr6_delete_leaf_subdept решает другую задачу: удалить подразделение только если оно не держит структуру и данные. Последовательно проверяется: (1) запись с таким ид существует; (2) нет дочерних строк в подразделение с ид_родительское = удаляемому ид — иначе дерево организации разорвётся; (3) нет строк штатное_расписание на это подразделение; (4) нет приёмов с этим ид_подразделения. Любое нарушение приводит к RAISE EXCEPTION с поясняющим текстом (в сообщении явно указано, какое именно условие не выполнено). Только если все проверки пройдены, выполняется DELETE FROM подразделение.

Идея для отчёта: сравнить с «сырым» DELETE, когда пользователь получил бы ошибку внешнего ключа без понятного объяснения, на каком именно условии целостность нарушена.

══════════════════════════════════════════════════════════════
04_fn_aggregate.sql — функция, возвращающая одно число
══════════════════════════════════════════════════════════════

Функция lr6_sum_staff_units объявлена на чистом языке SQL (не PL/pgSQL), возвращает bigint и помечена как STABLE: для одних и тех же аргументов в рамках запроса результат не меняется, что позволяет оптимизатору кэшировать вызовы. Тело — один SELECT: сумма количество_единиц по штатное_расписание для заданного ид_подразделения, с COALESCE(...,0) на случай отсутствия строк. В отчёте можно показать встраивание функции в обычный SELECT как в «чёрный ящик», вычисляющий агрегат по параметру.

══════════════════════════════════════════════════════════════
05_proc_stats_temp.sql — сводка по подразделениям во временную таблицу
══════════════════════════════════════════════════════════════

Процедура lr6_fill_stats_temp каждый вызов пересоздаёт TEMP-таблицу lr6_stat: сначала DROP IF EXISTS, затем CREATE TEMP TABLE с колонками под итоговые показатели. Вставка идёт одним INSERT … SELECT по всем строкам подразделение: для каждого подразделения в SELECT-списке вычисляются скалярные подзапросы — число строк штата, вызов уже написанной lr6_sum_staff_units(пд.ид), и число различных сотрудников по приёмам (COUNT DISTINCT по прием). Так в одном проходе собирается «панель показателей» без необходимости писать четыре отдельных запроса на клиенте.

Временная таблица видна только текущей сессии и исчезает при закрытии соединения; это удобно для отчётных снимков, не засоряя общую схему.

══════════════════════════════════════════════════════════════
06_batch_control_flow.sql — циклы и условия без сохраняемой процедуры
══════════════════════════════════════════════════════════════

В PostgreSQL нет «пакета» в смысле Oracle; вместо этого используется анонимный блок DO $$. Внутри объявлены переменные, затем цикл FOR по курсору «все ид из подразделение по порядку»: для каждого ид проверяется EXISTS по прием — есть ли хотя бы одна строка приёма в этом подразделении. Счётчик v_cnt накапливает количество таких подразделений. После цикла RAISE NOTICE выводит итог в сообщения клиента. Второй фрагмент — чисто учебный WHILE с обратным отсчётом от 3, чтобы показать синтаксис цикла с условием.

В отчёте стоит пояснить: DO не создаёт именованного объекта в каталоге, блок выполняется один раз при запуске скрипта; NOTICE читают на вкладке сообщений в pgAdmin или в консоли psql.

══════════════════════════════════════════════════════════════
07_fn_scalar.sql и 08_fn_table.sql — две формы пользовательских функций
══════════════════════════════════════════════════════════════

lr6_child_count — скаляр: на вход ид сотрудника, на выход целое число — количество строк в дети. Удобно вызывать в SELECT рядом с полями сотрудника, получая для каждой строки своё значение «число детей» без LEFT JOIN и группировки.

lr6_direct_subdepts — табличная: RETURNS TABLE(ид, наименование). В теле один SELECT с условием на иерархию: если параметр p_родитель NULL, возвращаются только корневые подразделения (где ид_родительское IS NULL); если не NULL — все строки, у которых ид_родительское равен переданному родителю. Так получают «один уровень» дерева без рекурсии. В отчёте можно сравнить: скалярная функция «встраивается» как столбец, табличная — как источник строк после FROM или в CROSS JOIN LATERAL.

10_demo_transaction.sql (по желанию)
══════════════════════════════════════════════════════════════

Файл демонстрирует обёртку BEGIN … CALL … ROLLBACK: изменения процедуры видны внутри транзакции до отката, после ROLLBACK база возвращается к состоянию на начало блока. Это практичный приём для проверки логики на живых данных без постоянных повреждений учебного дампа.
