Методичка: глава 8, п. 8.4 — представления, индексы, планы выполнения, при необходимости права доступа. Вариант 12. СУБД: PostgreSQL 11+.

══════════════════════════════════════════════════════════════
Что такое представление и зачем оно в этой лабораторной
══════════════════════════════════════════════════════════════

Представление (VIEW) в PostgreSQL — именованный запрос, который при обращении подставляется в текст запроса пользователя (правило «расписывания» view). У представления нет собственных строк в смысле физического хранения данных: при SELECT из lr8_vw_* СУБД читает базовые таблицы прием, сотрудник, подразделение и т.д. Это удобно для отчётов и приложений: один раз описали сложные соединения и подписи столбцов, дальше работают с «виртуальной» таблицей с понятными именами полей.

Объекты ЛР8 имеют префикс lr8_. Перед установкой — как обычно, lab1 и lab2; перед переустановкой — lab8/09_drop_lr8_objects.sql.

══════════════════════════════════════════════════════════════
01_view_priyom_details.sql — «расшифрованный» приём
══════════════════════════════════════════════════════════════

Представление lr8_vw_priyom_details строится от таблицы прием. К каждой строке приёма через INNER JOIN подтягиваются сотрудник (ФИО и ид), подразделение (наименование), должность (наименование и категория). В списке SELECT столбцы переименованы с префиксами прием_, сотрудник_, подразделение_, должность_, чтобы в выборке не путать ид разных сущностей.

Смысл для практики: отчёт «кто где и на какой должности принят» можно строить одним SELECT из представления, не повторяя четыре соединения в каждом отчётном запросе. В отчёте можно отметить: представление не дублирует данные, оно лишь задаёт «окно» над ними; изменение базовой таблицы прием сразу отразится в следующем SELECT из представления.

══════════════════════════════════════════════════════════════
02_view_shtat_enriched.sql — штат с человекочитаемыми названиями
══════════════════════════════════════════════════════════════

lr8_vw_shtat_enriched начинается от штатное_расписание и соединяет его с подразделение и должность. В результате каждая строка штата содержит не только числовые ид, но и подписи: как подразделение называется, как называется должность и какова её категория (инженер, техник, прочее). Это типичный приём нормализованной схемы: в операционных таблицах хранятся только ключи, а для аналитики и печатных форм удобнее готовое представление.

══════════════════════════════════════════════════════════════
03_view_subdept_tree.sql — обход иерархии рекурсией
══════════════════════════════════════════════════════════════

Иерархия подразделений задана полем ид_родительское: у корня оно NULL, у дочерних — ссылка на ид родителя. Рекурсивный запрос WITH RECURSIVE состоит из двух частей, объединённых UNION ALL. Первая часть (якорь) выбирает все строки, у которых ид_родительское IS NULL — это вершины дерева; им приписывается уровень 0 и путь_наименований равный собственному наименованию. Вторая часть (рекурсивная) присоединяет к уже найденному множеству tree дочерние строки подразделение: условие соединения c.ид_родительское = t.ид означает «взять детей текущего узла из предыдущего шага рекурсии». Уровень увеличивается на единицу, а путь дописывается через разделитель « / ».

Рекурсия в представлении удобна тем, что глубина дерева не зашита в запрос: добавили уровень вложенности в данные — представление автоматически покажет новые уровни. В отчёте важно словами описать роль якоря и шага UNION ALL и почему бесконечный цикл здесь невозможен при корректных данных (ациклическое дерево).

══════════════════════════════════════════════════════════════
04_indexes.sql — дополнительные B-tree индексы
══════════════════════════════════════════════════════════════

Первичные ключи и UNIQUE в схеме lab1 уже создают индексы на ключевых столбцах. Файл добавляет одностолбцовые индексы на столбцы, по которым чаще всего фильтруют или соединяют в запросах: ид_сотрудника, ид_подразделения, ид_должности в прием; ид_сотрудника в дети, перевод, увольнение; ид_подразделения в штатное_расписание. Имя каждого индекса с префиксом lr8_idx_; используется IF NOT EXISTS, чтобы повторный запуск скрипта не падал.

Идея для пояснения в отчёте: при выборке WHERE прием.ид_сотрудника = ? планировщик может использовать Index Scan вместо полного Seq Scan по всей таблице прием — на больших объёмах это снижает чтение страниц с диска. Цена — дополнительное место на диске и небольшое замедление INSERT/UPDATE/DELETE в этих таблицах, потому что индекс тоже надо обновлять.

05_explain_demo.sql — как читать план
══════════════════════════════════════════════════════════════

Команда EXPLAIN (с опциями COSTS, иногда VERBOSE) не выполняет запрос в смысле возврата строк пользователю, а выводит дерево операций, которое планировщик построил бы для выполнения. На учебной базе с малым числом строк часто остаётся Seq Scan: оптимизатор считает, что дешевле прочитать всю маленькую таблицу, чем лезть в индекс. Это не ошибка; в отчёте как раз и фиксируют «на малых данных план не изменился», но видно структуру: Nested Loop vs Hash Join, оценка числа строк и стоимости.

Второй и третий запросы в файле строят планы по SELECT из представлений — план обычно показывает вложенные Seq Scan или Index Scan по базовым таблицам «под» представлением. Имеет смысл приложить два фрагмента вывода EXPLAIN — до и после создания индексов из 04 — если методичка требует сравнение; если план идентичен, это честно написать в выводах.

══════════════════════════════════════════════════════════════
06_grants_example.sql — права на представления (по заданию)
══════════════════════════════════════════════════════════════

Фрагменты с CREATE ROLE и GRANT обычно закомментированы: на учебном сервере студенту редко дают суперпользователя. Смысл примера — показать модель «приложение читает только через представление»: роли lr8_reader выдают SELECT на lr8_vw_*, но не на базовые таблицы, чтобы не раскрывать лишние столбцы или не давать прямой путь к изменению данных. В отчёте это можно изложить концептуально, даже если скрипт не запускался.
